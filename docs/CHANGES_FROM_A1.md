## Task 3: blockade deadlocks

Task 2's 100-seed run found 11 games that hit the 500-round cap. Most were **mutual blockade deadlocks**: two blocks on neighbouring cells, moving towards each other, each stopping the other (seed 4: Blue B3+B4 on cell 2 moving counterclockwise, Yellow Y3+Y4 on cell 1 moving clockwise). Strategies kept choosing the blocked piece, `Game` never tried another, and only a triple six eventually broke a block.

| # | What changed | Rule | Why |
|---|---|---|---|
| 1 | **Fallback to other pieces.** When the chosen piece cannot make its full move (blocked, overshoots Home, in briefing, or its block cannot move), the game asks the same strategy again with that piece excluded (`Player.choosePiece(..., excluded)`), so the fallback follows the player's own preferences. The throw is ignored only when no piece can move. | Rule 7 | A1 gave up after the first choice and printed "does not have other pieces ... to move" even when it had them. That was the main cause of the deadlocks. |
| 1b | **Blue exception.** `MoveStrategy.triesOtherPiecesWhenBlocked()` is `true` by default and `false` for `CyclicStrategy`. Blue still skips when its cycled piece cannot move, and prints "Blue keeps to its cycle and does not move another piece instead." | Blue behaviour | Sticking to the cycle is Blue's defined behaviour. |
| 1c | **Check before moving.** `Game.checkMove` decides whether a move is possible without changing anything, and only then is the move applied. The "blocked" branch inside `landOnMainPath` moved into `moveUpToBlockOrSkip`. | Rule 7 | A1 discovered a block halfway through applying the move (counterclockwise pieces had already counted an approach pass), so it could not safely try another piece. |
| 1d | A piece that cannot use its home straight yet (T-7) and overshoots Home now continues round the main path instead of reporting "exact roll required". A roll reduced to 0 cells (Sick effect on a 1) counts as "cannot move". | Rule 10 / T-7 | Only a piece that is actually entering the home straight needs an exact roll. |
| 2 | **No change** to the partial move: verified by test. When no other piece can move, the blocked piece moves to the cell before the block and prints "Moved the piece to square L3 which is the cell before the block." This now happens only after the fallback has failed, and also applies to blocks. | T-3 | Already correct. |
| 3a | **Every block can move as a unit**, by roll ÷ pieces (integer division), in the direction of the piece with the longest distance to its approach cell. A1 only did this for blocks whose pieces had different directions; same-direction blocks never moved together. | T-4 | In seed 4 both Blue pieces moved counterclockwise, so the Blue block could never move as a unit or capture. |
| 3a' | **Interpretation:** if the block's own move is impossible (blocked, or roll too small for its size), the chosen piece leaves the block and moves alone in its own direction ("leaves the block ... (Rule T-5)"). | T-4 / T-5 (gap) | When blocks could *only* move as a unit, 76 of 100 games hit the cap, because blocks of different sizes jammed each other permanently. Letting a piece leave a stuck block keeps the game moving and gives T-5 a purpose. **Please confirm this matches the specification.** |
| 3a'' | **Interpretation:** a block stops on its own approach cell, and pieces on their approach cell move individually. | T-4 (gap) | Otherwise a block could never enter its home straight and would circle forever. |
| 3b | **Block capture.** A block landing on an opposing block of the same size captures it: all captured pieces go to base, and each capturing piece's capture count goes up by 1. Landing on a different-size block is not allowed (treated as blocked, T-3). A block may also capture a single piece. A1's `captureOpponentBlock` was unreachable code and incremented only one piece's count; it has been removed. | T-8 | A1 could never capture a block. |
| 3c | Seed 4's deadlock position is now a test: Blue rolls 2, its block moves 1 cell and captures the Yellow block. | T-8 | Proves the deadlock can be broken. |
| 3d | Moving a block no longer overwrites each piece's direction (A1 called `setDirection(blockDir)` on every piece). | T-5 | A piece that leaves a block must keep its own original direction. |
| 3e | Triple six now breaks **each** block separately (`Player.getBlocks()` returns one group per cell). In each block all pieces but the first move 6 cells in their own direction. | T-6 | A1 merged all block pieces into one list, so with two blocks the second block moved entirely and could re-form at its new cell. |
| 4 | **Stalemate rule (fills a gap in the specification).** If no capture and no piece reaching Home happens for 120 rounds, the game prints "No progress for 120 rounds: the game is declared a stalemate." Remaining players are ranked by pieces Home (more is better), then by total cells left to travel (fewer is better; a base piece counts 57 = 1 out + 50 to the approach + 6 into Home). The 500-round cap stays as the final safety net. | Spec gap (T-7) | T-7 makes a piece enter its home straight only after a capture, so a game can become impossible to finish: no reachable opponents, or pieces circling forever. The specification does not say how such a game ends. See the threshold note below. |
| 4b | `GameBuilder.withMaxRounds` / `withStalemateRounds` (tests only, defaults 500 / 120). Package-private test hooks on `Game`: `playerOf`, `playRoll`, `playTurn`, `handleTripleSixRule`, `declareStalemate`. | (none) | Let tests set up exact board positions and force the cap and stalemate paths. |

**Stalemate threshold.**
- *Old build, as asked:* measured over the 89 Task 2 games that finished normally, the longest stretch without progress was **205 rounds**. Every long stretch (205, 174, 157 and 145 rounds) turned out to be a blockade deadlock that a triple six eventually broke. Seed 42, for example, had 964 ignored throws and 1 move in its 205-round stretch. That number measures the bug, not normal play, and 1.5 × 205 ≈ 310 would not fit inside the 500-round cap anyway.
- *After the fixes above:* all 100 games (seeds 1–100) finish normally. The longest stretch without progress is **80 rounds** (seed 93; the mean of each game's longest stretch is 23.8). 1.5 × 80 = **120 rounds**, which is the threshold used.

**What was added**

| # | What | Pattern / principle | Why |
|---|---|---|---|
| 1 | `ludo.shared.json`: hand-written `JsonWriter` (compact, so canonical), `JsonParser` (recursive descent, rejects malformed input with the position) and `JsonObjects` (typed getters that name the bad field). | (none: no JSON library allowed) | The protocol needs JSON, and only JDK classes are allowed. | 2 | `ludo.shared.protocol`: `SnapshotCodec` (fixed field order, colours always Red, Green, Yellow, Blue), `StateHasher` (SHA-256 of the canonical JSON, hex), `EventType`, `RequestType`, `DecisionKind`, the six event records and the four request records (sealed interfaces `ServerEvent` and `ClientRequest`). | Value Object; Single Source of Truth | Server and clients must encode and hash a snapshot identically. | 5 | Coordinator states `WaitingForPlayers`, `AwaitingRoll`, `AwaitingDecision`, `AwaitingAcks`, `Pacing`, `Paused`, `GameOver`. | 6 | `RemoteTurnGate` (implements `TurnGate`) and `RemoteMoveDecider` (implements `MoveDecider`). | Adapter / Remote Proxy; Dependency Inversion (the Task 4 ports) | Game calls the same ports as before and does not know the players are remote. |
| 7 | `BufferingEventListener` collects the game's messages for the next STATE (and echoes them to the console). | Observer (concrete observer) | Clients show the same log the console game prints. |
| 8 | `Broadcaster`: event-stream list in a `CopyOnWriteArrayList`; all socket writes on one `sse-writer-<id>` thread per game. `EventSink` is the port the HTTP layer implements (`SseSink`). | Dependency Inversion; thread confinement for sockets | A slow or dead client can never block the game thread. | 9 | HTTP tier `LudoHttpServer` / `GamesHandler` on `com.sun.net.httpserver`, fixed pool of non-daemon `http-worker-N`. GET /state and GET /games read `volatile` immutable values only. | Separation of tiers | Reads never wait for the game thread. |

**Deviations from the original CLAUDE.md plan (CLAUDE.md updated)**

| # | Planned | Now | Why |
|---|---|---|---|
| D1 | Ack barrier with `Phaser` | A thread-confined `EnumSet` (`AckBarrier`) | ACKs reach the barrier through the command queue, so only the game thread ever touches it. A Phaser coordinates several threads; here it would only wrap a set that one thread checks off. |
| D2 | Pacing via `ScheduledExecutorService` | The game thread polls its queue until the turn-delay deadline | A scheduled task would need a second thread to hand the turn back to the game thread. Polling keeps the game thread answering requests during the delay and never sleeps. |
| D3 | States `AwaitingMove`, "client sends MOVE" | `AwaitingDecision`, "client sends DECISION" | Game asks two kinds of question (which piece; bring a piece out on a six?), sometimes several per roll (Rule 7 fallback). Each gets its own decisionId. |
| D4 | "Version incremented on every broadcast" (task brief) | Version + 1 on every **STATE** broadcast; SSE event ids are a separate counter | If PAUSED or DECISION_REQUEST also bumped the version, a slow client's still-valid answer would turn stale. The version now means exactly "state changes so far". |
| D5 | DECISION_REQUEST(colour, decisionId, kind, roll, candidates, version) | It also carries the snapshot | Game asks with the snapshot taken *after* the dice roll, which has not been broadcast as STATE yet. The client strategy needs exactly that snapshot to decide as the console game does. |
| D6 | Resume after a timeout "when that client reconnects" | Resumes when the missing answer arrives **or** the client reconnects. A reconnect is sent the STATE and the open request at once, then gets a fresh move timeout. | A client that was only slow should not have to reconnect. |
